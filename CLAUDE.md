# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Помощник для собеса (PHP/Symfony, финтех + фуллстек), тёмная тема. Открывается на https://sobes.local (домен в `/etc/hosts`, TLS через общий nginx-proxy). Главная — три плитки по центру: **Суфлёр** (`#suffler`), **Вакансии** (`#monitoring`), **Запись встречи** (`#record`); сайдбара на главной нет. Данные в **PostgreSQL**, отдаются тонким **PHP-API** с кэшем в **Redis**. **UI шпаргалки убран 03.08.2026 (просьба Ивана): ни поиска, ни карточек, ни личных заготовок на экране.** База из 1449 карточек по 43 темам живёт дальше — её грузит `GET /cards` и она идёт справкой модели в суфлёре (RAG), плюс из неё скорятся вакансии. Всё крутится в Docker.

## Команды (всё в Docker)

```bash
docker compose up -d --build                          # поднять/пересобрать стек (web, php, postgres, redis)
docker compose exec php php /var/www/api/seed.php      # (пере)залить БД из public/data/parts/*.json + db/*.json
docker compose down                                    # стоп (данные в volume sobes-pgdata сохраняются)
```

Проверять UI **только через расширение Chrome** (claude-in-chrome MCP), не через внутренний preview — внутренний preview не видит API/БД. Ассеты версионируются `?v=N` в `public/index.html` (бампать на всех `<link>/<script>` при правке фронта, иначе браузер отдаст старьё из кеша).

## Данные и бэкенд

- **Postgres** (`sobes-postgres`, БД/юзер/пароль `sobes`): `db/schema.sql` — таблицы `categories`, `questions` (q/a/detail/code/tags/weight/pinned/edited/orig/sort_order), `settings` (личные заготовки: self/task/jobs/ask), `sources` (источники мониторинга вакансий: kind `tg`|`account`, title, value [имя файла для tg / URL для account], login, password [для account, локально plaintext], enabled, `auto_apply` [авто-отклик без подтверждения для этого источника], `last_msg_id` [id последнего проанализированного тг-сообщения]), `vacancies` (найденные релевантные вакансии, score выше порога — тг-автопрогон >50, /scan_all >70: source_id, chat, msg_id, score, title, reason, link, text, `link_text` [полное описание вакансии, вытянутое по ссылке через WebFetch], `mismatches` [JSONB-массив главных несоответствий резюме], + автоотклик: `apply_status` [new|queued|approved|applied|direct|done (работа закончена)|needs_manual|skipped], `applied_at`, `cover_letter`, `apply_note`; + компания: `company` [название работодателя], `company_url` [найденный сайт/раздел вакансий вне источника], `hr_contacts` [JSONB-массив прямых контактов нанимающей стороны: {kind: email|tg|linkedin|phone|site|other, value, name, note, source}]), `agent_log` (лог работы автопрогона: kind, message, meta, created_at — видно на странице «Лог агента»). Источник правды.
- **Сид**: `api/seed.php` (запуск в php-контейнере) читает `db/categories.json` (порядок+названия), `public/data/parts/<key>.json` (карточки с полем `weight`), `db/personal.json`. **`TRUNCATE questions` — перезаливаются ТОЛЬКО вопросы**; категории и personal вставляются `ON CONFLICT DO NOTHING`, т.е. их правки в БД НЕ затираются пересидом (файлы `db/*.json` — только первичный бутстрап). `orig` = снимок карточки для «вернуть оригинал». Если правил `db/personal.json` и надо ФОРС-залить в БД (перезаписать) — `docker compose exec php php /var/www/api/refresh_personal.php` (вопросы/закрепы не трогает). **Добавить НОВЫЕ карточки без пересида** (полный `seed.php` снёс бы правки/закрепы через TRUNCATE) — дописать в `parts/*.json` и `docker compose exec php php /var/www/api/seed_append.php`: вставляет только отсутствующие `(category_key, q)`, существующие строки/закрепы не трогает.
- **Redis** (`sobes-redis`): кэширует собранный JSON под ключом `sobes:cards`; любая правка делает `DEL` (см. `cacheBust()`).
- **API** `api/index.php` (php-fpm, PDO+phpredis, без фреймворка). Роуты после `/api`:
  - `GET /cards` — `{categories, items, personal}` из кэша (на промахе собирает из БД и кэширует).
  - `POST /cards/{id}/pin {pinned}` · `POST /pins/clear` — закрепы.
  - `PATCH /cards/{id}` (q/a/detail/code) → `edited=true` · `POST /cards/{id}/reset` → восстановить из `orig`.
  - `PATCH /personal/{self|task|jobs|ask}` {title, body} — правка личных заготовок.
  - `GET /tg-files` — список файлов выгрузки из `.claude/tg_history` (папка примонтирована в php как `/var/www/tg_history:ro`).
  - `GET /sources` (пароль НЕ отдаёт, только `login`+`hasPassword`+`autoApply`) · `POST /sources {kind,title,value,login?,password?}` (уникальность по `(kind,value)`, дубль → `{ok:true,existed:true}`) · `PATCH /sources/{id} {enabled?,auto_apply?}` · `DELETE /sources/{id}`.
  - `GET /vacancies` (отдаёт `chat` [имя источника, метка на карточке] + `kind` источника + apply-поля; `sourceId` тоже есть, но UI-фильтр по источникам убран) · `DELETE /vacancies/{id}` — найденные вакансии · `POST /analyze/request` · `GET /analyze/status`.
  - `GET /log` — последние записи лога агента (новые сверху) · `POST /log {message, kind?, meta?}` — добавить запись. Агент из bash пишет через CLI `api/log.php` (stdin JSON), фронт читает `GET /log` на странице «Лог агента».
  - Автоотклик: `PATCH /vacancies/{id}/apply {apply_status?,cover_letter?,apply_note?}` (ставит агент; `applied` проставляет `applied_at` и гасит дубли группы в `skipped`, число ушедших возвращается полем `dupes`; `skipped` самой строке через этот роут НЕ ставится — только юзером) · `POST /vacancies/{id}/approve` (юзер одобряет: queued/needs_manual→approved) · `POST /vacancies/{id}/skip` (юзер отказался навсегда → `skipped` у ВСЕЙ группы дублей (заголовок + компания); строки остаются в БД, иначе скан вставит заново, а фильтра под них нет — просто исчезают из выдачи) · `PATCH /vacancies/{id}/company {company?,company_url?}` (сохранить найденный сайт компании) · `PATCH /vacancies/{id}/contacts {hr_contacts:[…],apply_note?}` (прямые контакты HR; непустой список → статус `direct`, вычистили все → откат в `applied`; `skipped` не воскрешает) · `POST /vacancies/{id}/done {apply_note?}` (работа по вакансии закончена → `done` + гашение дублей группы) · `POST /applied/check` (флаг сверки откликов; кнопки «✅ Обновить» и «🔄 Прогнать сейчас» из UI убраны, роуты `/applied/check` и `/analyze/request` оставлены как флаг-механика).

**Анализ вакансий (AI-матчинг):** `api/scan_tg.php` выдаёт новые тг-сообщения (id > last_msg_id) → Claude по каждому тянет полное описание вакансии по ссылке из поста (WebFetch, т.к. в тг-посте обычно только заголовок) и оценивает на соответствие резюме (`db/personal.json` / `[[user-resume-profile]]`) с учётом требуемого английского относительно B1 кандидата, оставляет score>70, выписывает `mismatches` (главные несоответствия) → `api/save_results.php` (stdin JSON `{matches, last}`; поля matches: source_id/chat/msg_id/score/title/company/reason/link/text/link_text/mismatches; `company` — работодатель из текста, по нему дедуп отличает одинаково названные вакансии) пишет `vacancies` + двигает `last_msg_id` + снимает флаг. **Тг-вакансии сохраняются сразу со статусом `needs_manual`** (апдейт по `source.kind='tg'`) — отклик на них всегда руками (контакт в самом посте, автоформы нет), поэтому они сразу уходят в «Ручной разбор», минуя «Новые»; сайтовые (`account`) сохраняются как обычно в `new`. Промпт скоринга — `scripts/monitor_prompt.txt`. Ручной/сессионный прогон: скан → воркфлоу (по агенту на чат, каждый фетчит ссылки и скорит) → save. Фронт: карточка показывает score/title/reason, блок «⚠ Несоответствия», ссылку «открыть» и тоггл «Текст сообщения» (пост в тг + описание по ссылке). **Автопрогон тг — локальная плановая задача (БЕЗ API-ключа).** Планировщик Claude Desktop `sobes-monitor-tick` (`~/.claude/scheduled-tasks/`, крон `7 * * * *` — раз в час, пока ноут включён и Claude Desktop открыт; если приложение было закрыто — выполнится при следующем запуске) на каждом прогоне читает playbook `scripts/agent_run.md` и делает всю работу САМ, своей головой (внешний ключ не нужен — скорит сам агент в сессии): старт-лог → `scan_tg.php` (новые сообщения) → скоринг каждого под резюме по `monitor_prompt.txt`, но с **порогом 50** (не 70) → релевантные (score>50) через `save_results.php` в «Новые» → **шаг C.4 «Прямые контакты»** (до 10 hh-вакансий из «Откликнулся» за прогон: ищет контакты HR, нашёл → `direct`, нет → `done`) → лог на каждом шаге через `api/log.php` (видно на странице «Лог агента», #log). Шаг C.4 идёт и в фоновом тике: он на WebFetch/WebSearch, браузер ему не нужен — в отличие от Фазы B и шагов отклика C.1-C.3, которые в фоне не запускают вообще. Прежний launchd-крон (`monitor_run.sh` + `ANTHROPIC_API_KEY`) больше НЕ используется — headless Claude в фоне/кроне даёт 401; `monitor_run.sh`/`com.sobes.monitor.plist` лежат в `scripts/` как история. **Сайты — Фаза B playbook, УСЛОВНО:** агент пытается сканить привязанные account-источники (hh.ru=13, Хабр=15) на КАЖДОМ прогоне, но только если доступен живой залогиненный браузер (Chrome-расширение). В чисто фоновом тике браузера обычно нет → Фаза B логируется как пропущенная (не падает); капча/2FA на сайте → сайт пропускается. Полноценно сайты идут, когда агент в живой сессии / «Run now» при открытом залогиненном Chrome. Флоу B: поиск за неделю (hh `search_period=7&schedule=remote&order_by=publication_time`, Хабр `remote=true&sort=date`) → отсев «Вы откликнулись» и уже сущих `(source_id,msg_id)` → скоринг>50 → `save_results.php` с `last:{}` (дедуп по ключу). Тг-источники: Remote IT (11), Gamedev (14), WEB3 (16), hh-бот "Работа и вакансии на hh.ru" (17 — тоже вакансии с hh.ru).

**Дедуп выдачи:** `GET /vacancies` схлопывает вакансии по нормализованному **заголовку + компании** (одна и та же вакансия с hh-сайта и из тг-канала hh-бота = дубль). На группу оставляет богатейшую строку: `applied` > `needs_manual` > с полным описанием (`link_text`) > выше score. В БД строки не трогаются, дедуп только на отдаче. Компания режет группу **только когда под одним заголовком встретились РАЗНЫЕ работодатели** (тогда «PHP-разработчик» двух контор не склеится); пока работодатель один или неизвестен — клеится как раньше, по заголовку. Строгое сравнение тут не годится: у тг-поста компании обычно нет, у сайтовой строки есть, и связка тг+сайт развалилась бы на две карточки, а значит на два отклика по одной вакансии (ловило ревью). Хост ссылки в ключ НЕ входит: половина живых групп держит дубли на разных площадках (hh + Хабр + тг), по хосту они бы перестали склеиваться — проверено на данных.

**Группа дублей = одна карточка, поэтому статус ставится всей группе** (хелпер `setDupeGroup` в `api/index.php`). `applied` через `PATCH /vacancies/{id}/apply` гасит дубли в `skipped` с пометкой «дубль: отклик отправлен по карточке #id» (старая заметка сохраняется через ` · `), оба запроса в одной транзакции, число погашенных возвращается полем `dupes`. Дублям НЕ ставится `applied`: сверка откликов на площадке их не найдёт и вернёт в `new` — вечный пинг-понг. Уже откликнутые и уже погашенные строки не трогаются никогда. **Нормализация заголовка/компании в PHP и в SQL обязана совпадать**: `vacNorm`/`vacNormSql` сворачивают пробелы и ТОЛЬКО ПОТОМ обрезают края — `btrim()` без аргумента снимает лишь пробел, и краевой `\n` от модели заставлял строку не совпадать даже сама с собой (кнопка «Пропустить» молча не срабатывала). `save_results.php` тримит `title` на входе.

**Скан сайтов (`kind='account'`, hh.ru/Хабр) — команда `/scan_all`:** только в живой сессии с залогиненным браузером (Chrome-расширение). Headless/крон для сайтов НЕдоступен: расширение (интерактивная авторизация) в фоне не поднимается + на входе бывает капча (Хабр — Yandex SmartCaptcha; капчи не проходим). Флоу: логин-чек (пароль подставляет менеджер паролей юзера, сам не ввожу) → поиск за неделю (hh `search_period=7&schedule=remote`, Хабр `remote=true&sort=date`) → шортлист по заголовку → отсеять уже применённые ("Вы откликнулись") и уже сущие `(source_id,msg_id)` → скоринг-воркфлоу (агент на вакансию, WebFetch+оценка, `msg_id`=числовой id из URL) → `save_results.php`. Ежечасно — `/loop 1h /scan_all` в открытой сессии.

**Прямой отклик (обход фильтров hh) — статус `direct` + `hr_contacts`.** hh часто гасит отклик своими фильтрами, поэтому по уже отправленным (`applied`) вакансиям ищем живые контакты нанимающей стороны и пишем мимо площадки. Отбор кандидатов: список откликов hh (`/applicant/negotiations`, статусы «Ожидание» и «Отказ») сверяется по `msg_id` с `applied` в базе. Список удобнее не кликать, а собрать в консоли вкладки: `fetch('/applicant/negotiations?page=N')` по страницам 0..9 + `DOMParser`, карточка = ближайший `div[class*="container--"]` к `a[href*="/vacancy/"]`, статус — первое слово текста карточки («Отказ» / «Просмотрен» / «Не просмотрен» = ожидание). SPA-фильтры сверху — кнопки без своего URL, дёргать их бесполезно. Замер 05.08.2026: 130 «Ожидание» + 57 «Отказ», из них 166 нашлись в базе. **Контактов в самих описаниях вакансий НЕТ** — hh их вычищает (0 email на 166 сохранённых `link_text`), искать надо снаружи. Что реально работает: **`career.habr.com/companies/<slug>` — самый урожайный источник** (в блоке «Контакты» лежит email компании по найму и имена рекрутёров: так нашлись Cbonds, MPSTATS, 585, Т-Банк, МГТС), затем карьерный сайт компании и PDF-описания вакансий на нём (у Фордевинда в PDF прямо «Почта для отправки резюме» + шаблон темы письма), затем объявление той же вакансии вне hh. **Грабли: WebFetch режет длинные страницы и блок контактов на Хабр Карьере в выдачу не попадает** — проверять сырым `curl ... | grep`, иначе получишь ложное «контактов нет». Найденное пишется `PATCH /vacancies/{id}/contacts` (см. роуты), вакансия уходит в фильтр «📬 Прямой отклик». **Контакт годен, только если его видели своими глазами на конкретной странице** — в `source` кладётся её URL; конструировать `hr@<домен>` по шаблону нельзя, письмо уйдёт в никуда.

**Планка работы — `score >= 70` (просьба Ивана 05.08.2026).** Скоринг и сохранение идут от 50 (видно картину рынка), но **вакансия со `score < 70` в работу не берётся: ни отклика, ни поиска контактов** — `save_results.php` кладёт её сразу в `done` с пометкой «соответствие ниже 70%», в «Новые» она не попадает. Планка живёт константой `SCORE_MIN` в `api/index.php` и `api/save_results.php`; её же проверяет роут `/contacts` (нашли контакты у слабой вакансии → всё равно `done`, не `direct`) и запрос очереди шага C.4. 05.08.2026 правило применено задним числом — 12 накопленных карточек (10 из «Прямого отклика», 2 из «Откликнулся») переведены в `done`, контакты в них сохранены.

**Статус `done` («🏁 Завершено») — работа по вакансии закончена, дальше ничего не делаем.** Туда уходят: **вакансия со `score < 70`** (см. выше); **вакансия в архиве на hh** (проверять ПЕРВЫМ делом, до поиска контактов, и не агентом, а `curl | grep` по полю `"validThrough"` — у закрытой дата в прошлом; текст «Вакансия в архиве» есть в разметке и у живой, по нему определять нельзя. Замер 05.08.2026: **93 из 225 откликов (41%) — архив**, молчание там про закрытую вакансию, а не про фильтры; вся очередь проверилась за пару минут и без единого токена); вакансия, по которой контактов не нашлось (`POST /vacancies/{id}/done` из шага C.4); карточка из «Прямого отклика» по кнопке «🏁 Завершить»; и **любой отклик НЕ на hh — сразу, минуя `applied`**. Последнее делает сам роут `/apply`: `applied` + ссылка без `hh.ru` → пишется `done` (хелпер `vacOnHh`, смотрит на `link`, а не на источник — тг-канал hh-бота ведёт на тот же hh). Смысл: прямой отклик нужен только против фильтров hh, на остальных площадках письмо доходит и вакансия закрыта. **Поэтому `applied` = «ждёт поиска контактов», и очередь шага C.4 это ровно он.** Очередь дополнительно отсекает вакансии, у которых дубль в группе уже `direct`/`done`: у дубля `applied` не гасится (факт отклика не затираем), иначе одну вакансию искали бы дважды. 05.08.2026 правило применено задним числом — 43 накопленных отклика не с hh (Хабр, geekjob, wantapply, getmatch, linkedin) переведены в `done`.

**Внешние формы отклика агент заполняет САМ — на всех источниках** (Lever, Greenhouse, Workable, Huntflow, форма на сайте компании). Открыть, заполнить все обязательные поля, **приложить резюме файлом** (вакансия на русском → `.claude/Резюме.pdf`, на английском и любом другом → `.claude/CV Ivan Grigorov.pdf`), отправить → `applied`. Что вписывать в поля — анкета `scripts/apply_form_answers.md` (контакты, локация, языки, зарплата, стек, стоп-ситуации); данных нет ни в анкете, ни в резюме — отвечать честно, не выдумывать. `needs_manual` теперь только для непроходимого: капча, регистрация с подтверждением почты/СМС, видео-визитка, объёмное тестовое. **Если резюме обязательное, а файл не грузится** (`file_upload` расширения берёт только приложенное юзером к чату, см. `[[resume-upload-blocked]]`) — вакансия не бросается: форма открывается в ОТДЕЛЬНОЙ вкладке, заполняется целиком кроме резюме и **вкладка остаётся открытой**, юзер сам пройдёт и приложит файлы. `apply_note` такой строки начинается с маркера **`[FORM_READY]`** — по нему следующий прогон видит, что форма уже подготовлена, и **второй раз её не открывает и не заполняет** (не гонять юзера по одним и тем же вкладкам); маркер уходит сам, когда статус станет `applied`. **Единственное исключение по письмам — hh.ru: сопроводительное туда агент сам не вписывает и не отправляет**, вакансия уходит в `queued` (Черновики) с черновиком письма и ждёт «Одобрить отправку»; на остальных площадках письмо пишется и отправляется агентом.

**Автоотклик — команда `/apply_vacancies` (запускать по запросу):** режим зависит от флага источника `sources.auto_apply`. **auto_apply=false (по умолчанию):** безопасная схема **черновик→одобрение в UI→отправка**. Работодателю в ручном режиме ничего не уходит без `approved`. ## Фронт (`public/`, без сборки, неймспейс `window.SOBES`)

Порядок в `index.html`: `api.js` → `search.js` → `app.js` (плюс `record.js` → `record-ui.js`). `app.js` при старте разводит роут по хешу и в фоне тянет `SOBES.api.load()` (`GET /api/cards`) — карточки кладутся в `SOBES._items` и в поисковый движок, экранов под них нет.

- **`api.js`** (`SOBES.api`): fetch-клиент — `load` + роуты мониторинга и записи. Плюс `streamPost` для суфлёра (роуты `/ask`, `/vision`) — дедлайны на первый чанк и на паузу, своя отмена, ошибки с полем `kind`; детали в [`docs/suffler.md`](docs/suffler.md).

- **`search.js`** (`SOBES.search`): движок в браузере, из UI больше не зовётся — жив ради `retrieve()` (справка модели для суфлёра). `reindex(it)` строит `_hay/_hayLat(транслит)/_tokens/_q/_a/_detail/...`. Поиск — AND по термам с весами полей; варианты терма: основа (стемминг рус), смена раскладки RU↔EN, транслит; пустой результат → fuzzy по Левенштейну. Сортировка: закреплённые → (в поиске: релевантность + подмешанный `weight`·0.03) → `weight` desc → индекс. **После правки текста карточки звать `engine.reindex(it)`**.
- **`app.js`**: весь UI (один IIFE). Мини-markdown (`mdInline/mdBlock`) и мини-подсветка (`highlightCode`+`KW`) без либ — отдаются наружу через `window.SOBES.md` (ими же рисует разбор записи). Четыре view в `#main`: `#home-view` (плитки), `#suffler-view`, `#monitoring-view`, `#record-view`; `route()` по hashchange, Esc → на главную. Сайдбар `#sidebar` целиком прячется на главной и в суфлёре (`#app:has(#sidebar[hidden])` → одна колонка), свой сайдбар остаётся у мониторинга и записи. `api.load()` зовётся в фоне только ради `engine.prepare(ITEMS)` — карточки нужны суфлёру как справка модели; упало — суфлёр просто отвечает без справки.

**Суфлёр (live-ответы ИИ) — своя страница `#suffler`, кнопка «🎧 Включить» в её шапке; подробности в отдельном документе [`docs/suffler.md`](docs/suffler.md).** Там же стрим `/ask` и `/vision`, keepalive-прокси к Anthropic, ASR-коррекция и RAG. Правишь что-то из этого — СНАЧАЛА прочитай его целиком, иначе наступишь на уже пройденное. Четыре самые дорогие грабли:
- функцию нельзя назвать `suffStream` — в том же IIFE уже есть `var suffStream` (MediaStream от `getDisplayMedia`) и молча перетирает объявление: `node --check` молчит, в рантайме `TypeError: suffStream is not a function`
- суть и детали ответа делит маркер `%%%`, а НЕ пустая строка — модель ставит её где попало, и под спойлер уезжает почти весь ответ
- дерево ответов живёт в своём контейнере `#suff-tree`, `render()` его не трогает — иначе первый же клик по категории сносит всю сессию ответов
- в nginx-прокси к Anthropic нужен явный `proxy_ssl_name api.anthropic.com`: `proxy_ssl_server_name on` берёт имя из `proxy_pass`, а там имя upstream-группы, и хендшейк рвётся с `SSL alert 40`

## Запись встречи (роут `#record`)

Кнопка «🎥 Запись встречи» в сайдбаре главной. Пишет **захват вкладки** (видео + звук созвона) вместе со **своим микрофоном**: обе дорожки сводятся через `AudioContext` в одну, на выходе один `.webm` (vp9+opus, 1.2 Мбит/с — примерно 500 МБ в час). Параллельно идёт **расшифровка речи**: звук вкладки и микрофон слушают ДВА отдельных распознавателя, поэтому в тексте видно, кто говорил. По репликам можно прыгать по видео. Кнопка «🎯 Точная расшифровка» перегоняет готовую запись через локальный whisper. Разбором записей занимается агент в чате, ИИ-обвязки в самом приложении нет (убрана по просьбе Ивана 03.08.2026).

- **Куда пишется:** файл на диск в `./recordings` (том, в git не лежит), метаданные и текст — в Postgres: `recordings` (title, file, mime, status `recording|done|failed`, size_bytes, duration_ms, `chunks` [счётчик принятых кусков], `transcript_kind` [live|whisper], `whisper_status` [''|queued|running|done|failed], `whisper_note`, started_at, finished_at) и `recording_lines` (recording_id, `t_ms` — смещение от старта, text, `speaker` [me|them|'']).
- **Заливка идёт кусками по 5с прямо во время встречи** (`MediaRecorder.start(5000)` → `POST /recordings/{id}/chunk?seq=N`, тело — сырые байты, php дописывает в конец файла). Так и память вкладки не пухнет, и при падении браузера записанное уже на диске. Очередь строго последовательная, кусок при ошибке НЕ выбрасывается, а повторяется; сервер по `seq` отбивает повтор после потерянного ответа (`{dup:true}`), иначе в файле были бы битые кластеры.
- **Роуты:** `GET /recordings` (список + число реплик) · `GET /recordings/{id}` (запись + вся расшифровка) · `POST /recordings` {title,mime} (заводит строку и пустой файл — права на папку ловим здесь, а не в середине встречи) · `POST /recordings/{id}/chunk?seq=N` · `POST /recordings/{id}/finish` {duration_ms} (пустой файл → `failed`) · `POST /recordings/{id}/lines` {lines:[{t,text}]} · `PATCH /recordings/{id}` {title} · `DELETE /recordings/{id}` (строка + файл).
- **Файлы отдаёт nginx, не php:** `location /rec/` с `alias /srv/rec/` — Range-запросы (перемотка) работают из коробки. Монтировать записи ВНУТРЬ `/usr/share/nginx/html` нельзя: том с `public/` подключён `ro`, и docker не создаст там точку монтирования (контейнер не стартует).
- **Лимиты под куски:** `client_max_body_size 64m` в `location /api/` (дефолтный 1m резал бы заливку 413-й) и `post_max_size = 64M` в `docker/php/php.ini` (в образ как `zz-sobes.ini`). Внешний nginx-proxy уже разрешает 108M.
- **Кнопка «Скачать» отдаёт видео и расшифровку сразу:** ссылка качает `.webm`, её обработчик рядом собирает `.txt` (шапка + реплики `[мм:сс] текст`) и сохраняет под тем же именем. Двоеточия и слэши из заголовка в имени файла режутся. Расшифровки нет — качается только видео, подпись кнопки это отражает.
- **Плеер на карточке свёрнут по умолчанию** (просьба Ивана 05.08.2026 — развёрнутые видео занимали по пол-экрана): кнопка «▶ Смотреть» разворачивает, `<video>` создаётся ЛЕНИВО при первом раскрытии (иначе `preload=metadata` дёргал файлы всех записей разом). Клик по реплике расшифровки разворачивает плеер сам и перематывает на таймкод.
- **Список записей рисует сам `record-ui.js`:** `route()` в `app.js` зовёт `SOBES.recUI.open()`, но сам `app.js` подключён РАНЬШЕ `record-ui.js` и на старте вызывает `route()` синхронно — при заходе прямо на `#record` (или F5) этот вызов уходил в пустоту и список не грузился. Поэтому модуль в конце сам делает `openIfRecord()` и слушает `hashchange`.
- **Фронт — два файла:** `record.js` (`SOBES.rec`: захват, микс, MediaRecorder, очередь заливки, распознавание; DOM не трогает, шлёт события в `SOBES.recUI`) и `record-ui.js` (страница: пульт в сайдбаре, живое превью, список записей, плеер, расшифровка, разбор). Запись живёт независимо от страницы — уход на главную или в мониторинг её НЕ прерывает, в сайдбаре горит красная точка `#rec-dot`.
- **Качество захвата выбирается в сайдбаре, по умолчанию лёгкое.** Замерено на живой встрече 04.08.2026: без ограничений Chrome отдавал **3356×2836** (полный retina-кадр), и программный vp9 на таком размере отбирал процессор у самого созвона — собеседник заикался. Профиль `light` (1280×720, 12 fps, vp8, 0.9 Мбит/с) снимает нагрузку, `sharp` оставляет исходный размер и vp9 для случаев, когда нужен читаемый код на расшаренном экране. Ограничения ставятся и в `getDisplayMedia`, и повторно через `applyConstraints` на треке — Chrome умеет проигнорировать первые.
- **Распознавание — ДВА движка сразу, а не один по миксу.** Раньше Web Speech слушал смикшированную дорожку и на наложении голосов терял куски целыми минутами (замер: 31 реплика на 16 минут встречи). Теперь звук вкладки и микрофон идут в разные `SpeechRecognition` (проверено: Chrome тянет два одновременно, `asrCount: 2, asrLive: 2`), каждая реплика помечается `speaker` = me|them. Не приняли дорожку — откат на один распознаватель по миксу. К финальным репликам применяется карта поломок ASR из `GET /asr-terms` — та же, что у суфлёра.
- **Точная расшифровка — локальный whisper.cpp, запускается САМА после остановки записи** (просьба Ивана 05.08.2026): роут `/finish` при непустом файле сразу ставит `whisper_status='queued'`, воркер подхватывает. Кнопка «🎯 Точная расшифровка» на карточке осталась для повтора и для записей, сделанных до автозапуска — она ставит в очередь вручную (`POST /recordings/{id}/transcribe`), а разбирает очередь **хостовый** воркер `scripts/whisper_transcribe.py` (`GET /transcribe/queue` → ffmpeg в wav 16кГц → `whisper-cli` с моделью `~/.cache/whisper-models/ggml-large-v3-turbo.bin` → `POST /recordings/{id}/lines` c `replace:true`). К whisper-тексту применяется та же карта поломок ASR, что и к живой расшифровке (`GET /asr-terms`) — whisper ломает термины по-своему («бэков»=backoff, «промэтис»=Prometheus, «декр»=Docker), и без словаря было 12 терминов из 16 вместо 16. Метки «я/собеседник» whisper не различает, поэтому воркер переносит их с черновой расшифровки по таймкодам.. В докере его держать незачем: считает он на процессоре машины, а модели лежат в домашней папке. **Воркер запускается сам**: launchd-агент `com.sobes.whisper` (шаблон `scripts/com.sobes.whisper.plist`, копия в `~/Library/LaunchAgents/`) стартует при входе в систему, `KeepAlive` поднимает его после падения, `ProcessType=Background` + `Nice 5` держат счёт в фоне. Логи — `~/Library/Logs/sobes-whisper.log`. Руками: `launchctl kickstart -k gui/$(id -u)/com.sobes.whisper` (перезапуск), `launchctl bootout gui/$(id -u)/com.sobes.whisper` (выключить), `python3 scripts/whisper_transcribe.py` (разовый прогон без агента). **Пока идёт запись встречи, воркер не считает** — проверяет `status=recording` перед каждым заданием и посреди очереди, иначе whisper отобрал бы процессор у живого созвона. **Параметры whisper подобраны замерами и трогать их без замера нельзя** (05.08.2026): `-bs 1` (greedy) вместо beam search — с дефолтным beam search модель на длинной русской речи уходит в бесконечный повтор: восьмиминутный кусок дважды висел по 25 минут и убивался таймаутом, а с greedy посчитался за 2:46; `--vad` с моделью `ggml-silero-v5.1.2.bin` (вырезает тишину — на ней и залипало); `-mc 0` (не тащить контекст между окнами); аудио режется на куски по 8 минут, у каждого таймаут 3× длительности — зависший кусок убивается, остальные доезжают, потери пишутся в лог. **В plist НЕ ставить `ProcessType=Background`**: с фоновым классом macOS резал долю процессора вдвое (замер: 8:54 против 6:55 на одном файле), `Nice 5` достаточно. **Замер 05.08.2026 на синтезированной речи 11.1 мин: 6:55 счёта (0.62× реального времени), 132 реплики, 16 технических терминов из 16.** Пока считает, страница сама обновляет статус раз в 15с.
- **Пауза записи — кнопка «⏸ Пауза» под «Начать запись»** (`MediaRecorder.pause/resume`): файл на паузе не растёт, распознавание останавливается, таймер стоит. Время считает `elapsed()` — от старта минус сумма пауз, потому что MediaRecorder пауз в файл не пишет; по нему же ставятся таймкоды реплик, иначе расшифровка разъезжается с видео. Проверено 03.08.2026: 6с паузы → в БД 22с, в файле 21.7с звука.
- **Микрофон подбирается сам, галочек в UI нет** (просьба Ивана 03.08.2026: микрофон и расшифровка — всегда). Chrome берёт системный вход по умолчанию, а он вполне может быть немым: замерено 03.08.2026 — «Микрофон MacBook Pro (Built-in)» при подключённых AirPods отдаёт РОВНО нули (ни одного ненулевого сэмпла даже с выключенными `noiseSuppression`/`autoGainControl`), при этом трек `live`, `enabled`, не `muted`, а разрешение `granted`. Из-за этого первая версия писала встречу без голоса Ивана. Поэтому вход подбирается перебором (`autoPick` в `record.js`): кандидаты сортируются — сначала явная гарнитура, потом «по умолчанию», встроенный микрофон ноутбука последним, — каждый слушается ~0.9с СЫРЫМ потоком (`echoCancellation/noiseSuppression/autoGainControl: false`; с шумодавом живой микрофон в тишине тоже отдаёт ровные нули и не отличим от немого), берётся первый с ненулевым сигналом. Первые 300мс замера пропускаются: bluetooth-гарнитура в этот момент ещё переключается в HFP. Сигнала не нашли — остаётся первый кандидат, то есть гарнитура, а не встроенный. Выбор кешируется в localStorage `sobes:rec-mic` и при следующем заходе НЕ перепроверяется (открытие bluetooth-входа занимает секунды) — перепроверка по кнопке ↻ и на старте записи; селект в сайдбаре позволяет переопределить. Полоска громкости от `AnalyserNode`; если микрофон молчит дольше 8с — статус кричит об этом прямо во время встречи.
- **Страница НЕ трогает микрофон при открытии — это принципиально.** На машине Ивана `getUserMedia` на неотвечающем входе подвешивает вкладку на десятки секунд (воспроизведено: `Runtime.evaluate` и инъекция скриптов отваливаются по таймауту). Поэтому при заходе рисуется только список из `enumerateDevices` (потока не открывает), а поток берётся в момент старта записи или по кнопке ↻. Все обращения к микрофону обёрнуты дедлайнами (`withDeadline`: 2.5с на пробу входа, 8с на весь перебор, 6с на открытие микрофона при старте) — зависший вход не должен срывать саму запись. И ещё: перебор входов сам порождает событие `devicechange`, поэтому обработчик сверяет состав устройств, иначе получается бесконечный цикл подбора.
- **Грабли:** MediaRecorder не пишет длительность в заголовок webm — у свежего файла `duration = Infinity` и перемотка мертва; лечится в `fixSeek()` (увести `currentTime` в конец, дождаться `durationchange`, вернуться в 0).

**Пул php-fpm — `docker/php/pool.conf`** (копируется в образ как `zz-sobes.conf`, перекрывает дефолтный `www.conf`): `pm = static`, 20 воркеров, `request_terminate_timeout = 120s`. Зачем: каждый ответ суфлёра держит воркер всё время стрима (5-11с), на дефолтных 5 воркерах сайт вставал колом — замер: при 8 параллельных стримах `/api/cards` отдавался **1.59с** вместо 0.03с. `dynamic` не спасает (поднимает воркеры постепенно, на всплеске всё равно 1.18с) — только `static`, тогда 0.038с. Воркер ест ~14 МБ, но за счёт copy-on-write весь контейнер занимает 25 МБ. Таймауты сведены: `CURLOPT_TIMEOUT` 90с (php→Anthropic) < `fastcgi_read_timeout` 100с (nginx→fpm) < `request_terminate_timeout` 120с — при зависании первым срабатывает curl и отдаёт внятную ошибку, а не обрыв. **Правка pool.conf требует `docker compose up -d --build php`.**

## Отдача (docker)

`docker-compose.yml`: `web` (nginx:alpine) монтирует `public/` ro, `recordings/` в `/srv/rec` ro и `docker/site.conf`, в сетях `proxy-network` (внешняя, общий reverse-proxy) + `sobes-internal`; роут `/api/` → `sobes-php:9000` (fastcgi). `php` (`docker/php/Dockerfile`: php-fpm-alpine + pdo_pgsql + redis + opcache) в `sobes-internal`, монтирует `api/`, `db/`, `public/`, `.claude/tg_history/` (ro) и `recordings/` на запись. Домен `sobes.local` — в общем nginx-proxy (см. память `local-domain-recipe`), сертификат mkcert.
